# T26: Swift parity capture script + parity tests enabled

**Phase:** 4 · **Deps:** T12 · **Crate(s):** `pf-api` (tests), `scripts/`, `fixtures/parity/` · **Size:** medium (≈150 lines script + 200 lines tests)

## Goal

Prove that PFRust answers the HTTP API exactly as the Swift app does for the same data (docs/testing.md, layer L6).
A shell script records every read-only API response from the **running Swift app** into `fixtures/parity/`. Rust tests load
the same fixture into PFRust and compare. Once the captures exist, the `#[ignore]` on the parity tests is removed.

> **Use the actual names from T12/pf-engine if they differ; do not add engine behaviour here.** If a parity test fails because
> PFRust differs, fix the bug in the owning crate (usually `pf-api` formatting or `pf-core`), and add a regression test there too.

## The capture script

Preconditions, which the script prints and checks:
1. The **Swift** PF app is running (not PFRust; both use port 8989). `curl -sf http://localhost:8989/api/scenarios` must succeed.
2. The Swift app holds **exactly** `fixtures/SampleData2.md`: Settings → Import from Markdown (wipes data) with
   `../SampleData2.md`. The script cannot verify this fully, so it asks `Loaded SampleData2.md into the Swift app? [y/N]`
   and also checks that `/api/accounts/balances?format=text` mentions "Main Checking" and "Rewards Card".
3. Accounts in that fixture: `Main Checking`, `Rewards Card`. Scenario: `New Car Savings`.

Requests to capture (all `GET`; `curl -s -o <file> -w '%{http_code}\t%{content_type}'`, URL-encode names with `%20`):

| name | path + query |
|---|---|
| `scenarios_json` / `_text` / `_md` | `/api/scenarios?format=json` / `text` / `markdown` |
| `balances_{fmt}` | `/api/accounts/balances?format={json,text,markdown}` |
| `balances_{fmt}_scn` | `…&scenario=New%20Car%20Savings` |
| `balances_reality_ci` | `/api/accounts/balances?format=json&scenario=REALITY` |
| `balances_bad_scenario_{json,text}` | `…&scenario=Nope` |
| `balance_{acct}_{fmt}` | `/api/accounts/{Main%20Checking,Rewards%20Card}/balance?format=…` |
| `balance_case_insensitive` | `/api/accounts/main%20checking/balance` |
| `balance_plus_in_query` | `/api/accounts/Main%20Checking/balance?scenario=New+Car+Savings` |
| `balance_not_found` | `/api/accounts/Nope/balance` |
| `tx_{acct}_{fmt}` | `/api/accounts/{acct}/transactions?n=10&format=…` |
| `tx_{acct}_all_json` | `…/transactions?n=100000&format=json` |
| `tx_{acct}_{fmt}_scn` | `…/transactions?n=10&format=…&scenario=New%20Car%20Savings` |
| `tx_default_n` | `/api/accounts/Main%20Checking/transactions` (default n = 10, json) |
| `unknown_route` | `/api/nope` |
| `export_markdown` | `/api/export/markdown` |

**Not captured:** `GET /api/db-path` (machine specific) and `POST …/import` (it mutates the Swift data). The import endpoint is
covered by T12's own tests. Write `manifest.tsv` and `meta.txt` (TZ from `readlink /etc/localtime | sed 's#.*/zoneinfo/##'`).
The script must be idempotent (it deletes old `*.body` first) and must never write outside `fixtures/parity/`.

## The parity tests (`crates/pf-api/tests/parity.rs`)

* `fn load_world()` builds a temp-file engine, sets the engine's clock to the capture date and its **time zone to the one in
  `meta.txt`** (the Markdown import converts timestamps with it), imports `fixtures/SampleData2.md`, and starts the API on port 0.
* One test per manifest line, generated by a loop inside a few tests (to keep the names stable):
  `parity_scenarios`, `parity_balances`, `parity_balance_single`, `parity_transactions`, `parity_errors`, `parity_export_markdown`.
  For each line: same status code; same content type (ignoring case and spaces); then the body compared as follows:
  * JSON: parse both with `serde_json`; compare structurally. Numbers compare within **0.005** (Swift converts Decimal to
    Double); key order is ignored (both sides sort, but do not depend on it).
  * text / markdown: exact byte equality after normalising line endings only.
  * `export_markdown`: exact equality after removing the whole `## Settings` section from both sides (bookmark values differ).
* On mismatch, print a unified diff (`pretty_assertions`) that names the manifest line.
* If `fixtures/parity/manifest.tsv` does not exist, each test prints `parity captures missing; run scripts/capture_swift_parity.sh`
  and **fails**. That is why they start `#[ignore]` (see testing.md); this task captures them, then removes the ignore.

## Steps

1. Write `scripts/capture_swift_parity.sh` (`set -euo pipefail`, `chmod +x`) and `fixtures/parity/README.md`.
2. Write `parity.rs` with `#[ignore = "needs captures from the Swift app (T26)"]`.
3. **Ask the user** to run the capture: quit PFRust, start the Swift app, import `SampleData2.md`, then run
   `scripts/capture_swift_parity.sh`. (An agent must not drive the Swift app's UI, and must not wipe the user's Swift data
   without explicit permission. The import wipes it! Recommend that the user first exports a backup from the Swift app.)
   If the user is unavailable, mark the task `blocked` with the instructions and stop here.
4. With the captures committed: run the tests, fix every mismatch in the owning crate (each fix gets a regression test there),
   and remove the `#[ignore]`.
5. Run Done-when.

## Pitfalls

- Swift prints Decimal-to-Double numbers like `-12.5` and `1234.56`; serde_json may print `-12.5` as well, but compare parsed values anyway.
- Swift's `JSONSerialization` with `.prettyPrinted` writes a 2-space indent and `"key" : value` (a space before the colon), with
  sorted keys where requested. serde_json's pretty printer writes `"key": value`. The parity test only demands structural
  equality for JSON, so this whitespace difference is acceptable. Note it in `fixtures/parity/README.md`.
- The Swift transactions list sorts by date desc; same-day ordering in Swift is unspecified. If same-day order differs, compare
  those rows as a set, and document it in `fixtures/parity/README.md`.
- Do not commit captures made from the user's **real** data; only from `SampleData2.md`.
